# Data model

This document describes the schema as implemented in
`internal/store/migrations/`. Where it and the migrations disagree, the
migrations are correct and this document is a bug.

## Conventions

- **Identifiers are UUIDs**, generated by the application. Runs are created on
  one node and referenced from others; a database sequence would force a round
  trip before the id is usable.
- **Enumerations are `text` with a `CHECK` constraint**, not native PostgreSQL
  enums. Adding a value to a native enum cannot always run inside a transaction
  alongside other DDL, and a `CHECK` is trivially alterable.
- **Every timestamp is `timestamptz`.** The application always passes UTC.
- **No triggers, views, materialized views, stored procedures or row-level
  security.** Behaviour that lives in the database is behaviour the tests cannot
  see and the code does not explain.

## Entities

### `workflows`

A versioned workflow definition.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | PK |
| `name` | text | no | |
| `version` | integer | no | `> 0` |
| `definition_yaml` | text | no | The canonical re-marshalling, so what is stored is what was hashed |
| `definition_hash` | text | no | sha256 of the canonical form |
| `created_at` | timestamptz | no | default `now()` |

**Unique:** `(name, version)`.

Registering the same bytes twice is a no-op. Registering *different* bytes under
an existing `(name, version)` is refused with `engine.ErrDefinitionChanged`: two
runs labelled the same version have to be comparable, or replay means nothing.

### `runs`

One execution of a workflow.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | PK |
| `workflow_id` | uuid | no | FK → `workflows(id)` ON DELETE RESTRICT |
| `status` | text | no | `CREATED\|QUEUED\|RUNNING\|SUCCEEDED\|FAILED\|CANCELLED` |
| `scenario_name` | text | yes | |
| `seed` | bigint | no | Always set, so a run with no scenario is still reproducible |
| `event_seq` | bigint | no | default 0, `>= 0`. The journal's counter |
| `correlation_id` | text | yes | |
| `failure_reason` | text | yes | |
| `created_at` | timestamptz | no | default `now()` |
| `started_at` | timestamptz | yes | |
| `completed_at` | timestamptz | yes | |

**Check:** a terminal status and a non-null `completed_at` imply each other.

**Deliberately absent:** `workflow_version`. `workflow_id` determines
`(name, version)`, and a duplicated version column can drift from the row it
points at. The join is a primary-key lookup. This is a considered deviation
from the original plan's domain sketch.

`event_seq` is the mechanism behind gapless sequence numbers. `event.Append`
increments it with `UPDATE ... RETURNING` inside the appending transaction,
which takes the row lock and rolls the number back with a rolled back append.
The same statement carries `WHERE completed_at IS NULL`, which is what makes a
run's terminal event its last.

**Indexes:** `(status, created_at DESC)` for the run list;
`(workflow_id, created_at DESC)`.

### `tasks`

One step of one run. **One row per step, not per attempt.**

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | PK |
| `run_id` | uuid | no | FK → `runs(id)` ON DELETE CASCADE |
| `task_name` | text | no | |
| `attempt` | integer | no | default 0, `>= 0`. Incremented at claim time |
| `max_attempts` | integer | no | `> 0`. Copied from the step's retry policy |
| `status` | text | no | `PENDING\|READY\|LEASED\|RUNNING\|SUCCEEDED\|FAILED\|RETRYING\|DEAD` |
| `worker_id` | uuid | yes | FK → `workers(id)` ON DELETE SET NULL |
| `lease_expires_at` | timestamptz | yes | |
| `scheduled_at` | timestamptz | no | When the task becomes claimable |
| `started_at`, `completed_at` | timestamptz | yes | |
| `input_ref`, `output_ref` | jsonb | yes | |
| `error` | text | yes | Truncated at 2048 characters |
| `idempotency_key` | text | no | The `run_id:task_name` prefix |
| `created_at`, `updated_at` | timestamptz | no | |

**Unique:** `(run_id, task_name)`.

**Checks:** holding a lease and having a `lease_expires_at` imply each other;
a task in `LEASED` or `RUNNING` must name a worker.

**Indexes:**
- `(scheduled_at) WHERE status = 'READY'` — the claim query's index. Partial, so
  it is proportional to work outstanding rather than to work ever created.
- `(lease_expires_at) WHERE status IN ('LEASED','RUNNING')` — the reaper's.
- `(run_id)`.

**Lifecycle** (`internal/engine/state.go`; every transition, legal and illegal,
is unit tested):

```
PENDING ──► READY ──► LEASED ──► RUNNING ──► SUCCEEDED
   │          │         │  │        │  │
   │          │         │  └────────┼──┴──► FAILED ──► RETRYING ──► READY
   │          │         │           │            └──► DEAD
   │          │         └───────────┴──► READY          (attempts exhausted)
   │          │            (lease expiry)
   └──────────┴──────────────────────────────────────► DEAD
                  (run cancelled, or upstream failed)
```

`FAILED` is **not** terminal: it is always resolved into `RETRYING` or `DEAD` in
the same transaction that records it. Terminal task states are `SUCCEEDED` and
`DEAD`.

### `task_attempts`

Append-only record of every execution start.

| Column | Type | Null |
|---|---|---|
| `task_id` | uuid | no |
| `attempt` | integer | no |
| `worker_id` | uuid | yes |
| `started_at` | timestamptz | no |

**Primary key:** `(task_id, attempt)`.

This primary key is the concurrency assertion. Two workers executing the same
attempt of the same task at once is a scheduler bug, and it surfaces here as a
constraint violation instead of as silent duplicate work. A legitimate
at-least-once duplicate — a lease expiring while the original worker is alive —
always carries a new attempt number and does not collide.

### `events`

The append-only run journal. **No row is ever updated or deleted.**

| Column | Type | Null | Notes |
|---|---|---|---|
| `run_id` | uuid | no | FK → `runs(id)` ON DELETE CASCADE |
| `seq` | bigint | no | `> 0`, gapless per run |
| `type` | text | no | One of 21 declared types |
| `task_name` | text | yes | NULL for run-scoped events |
| `worker_id` | uuid | yes | **Not** a foreign key — see below |
| `payload` | jsonb | no | Always an object, always carrying `"v"` |
| `occurred_at` | timestamptz | no | |

**Primary key:** `(run_id, seq)`.

**Check:** `jsonb_typeof(payload) = 'object'`.

`worker_id` is intentionally not a foreign key: the journal outlives the worker
rows it references, and purging dead workers must not rewrite history. The same
reasoning makes `task_name` a plain string here.

**Event types:** `RUN_CREATED RUN_QUEUED RUN_STARTED RUN_SUCCEEDED RUN_FAILED
RUN_CANCELLED TASK_SCHEDULED TASK_LEASED TASK_STARTED TASK_SUCCEEDED TASK_FAILED
TASK_RETRY_SCHEDULED TASK_LEASE_EXPIRED TASK_REQUEUED TASK_DEAD_LETTERED
WORKER_REGISTERED WORKER_HEARTBEAT WORKER_SUSPECT WORKER_LOST FAULT_INJECTED
SIDE_EFFECT_SKIPPED`.

**Payload versioning:** every payload carries `"v"`, stamped centrally by
`event.Encode` rather than by each struct. A decoder that meets a version it does
not know returns an error. A missing `"v"` is treated as unknown rather than as
version 1: every payload ReLab has written carries one, so its absence means the
row did not come from ReLab.

### `workers`

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | PK |
| `hostname`, `version` | text | no | |
| `status` | text | no | `HEALTHY\|SUSPECT\|LOST` |
| `capacity` | integer | no | `> 0` |
| `active_tasks` | integer | no | `>= 0` |
| `last_heartbeat` | timestamptz | no | |
| `registered_at` | timestamptz | no | |

**Index:** `(last_heartbeat) WHERE status <> 'LOST'`. Lost workers are terminal
and never re-examined, so they are excluded.

**Lifecycle:** `HEALTHY → SUSPECT` after 3 missed heartbeats, `SUSPECT → LOST`
after 5. `LOST` is terminal: a heartbeat from a lost worker is refused with
`engine.ErrWorkerLost`, because its leases have been handed on and letting it
return would leave two workers believing they own the same tasks.

### `side_effects`

The idempotency ledger.

| Column | Type | Null |
|---|---|---|
| `idempotency_key` | text | no (PK) |
| `run_id` | uuid | no |
| `task_name` | text | no |
| `result` | jsonb | no |
| `created_at` | timestamptz | no |

The key is `run_id:task_name:operation`. Run ids are UUIDs and task names are
validated to exclude `:` at parse time, so no two distinct triples can collide
by concatenation.

### `artifacts`

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | PK |
| `run_id` | uuid | no | FK → `runs(id)` CASCADE |
| `task_name`, `name` | text | no | |
| `sha256` | text | no | `CHECK (sha256 ~ '^[0-9a-f]{64}$')` |
| `size` | bigint | no | `>= 0` |
| `content_type` | text | no | |
| `created_at` | timestamptz | no | |

**Unique:** `(run_id, task_name, name)` — replay compares artifacts by task and
name, and two sharing both would make the comparison ambiguous.

**The bytes are not stored.** Only the hash. Replay compares hashes, and keeping
the content would make the database the wrong size for the job it does.

### `dead_letters`

| Column | Type | Null |
|---|---|---|
| `task_id` | uuid | no (PK) |
| `run_id` | uuid | no |
| `reason` | text | no |
| `attempts` | integer | no (`> 0`) |
| `last_worker` | uuid | yes |
| `created_at` | timestamptz | no |

### `schema_migrations`

`version` (PK), `name`, `checksum`, `applied_at`. The checksum recorded at apply
time is compared on every subsequent start-up, so an edited released migration
fails loudly rather than leaving half a fleet on a different schema.

## Referential integrity and deletion

Deleting a run cascades to its tasks, events, artifacts, side effects and dead
letters. Deleting a workflow is **restricted** while runs reference it: a run
whose definition is gone cannot be replayed, and replay is the product.

Deleting a worker sets `tasks.worker_id` to NULL rather than cascading. A task
outlives the worker that ran it.

## Data validation

Validation happens at three layers, deliberately:

1. **Parse time** — `internal/workflow` rejects cycles, duplicate step names,
   unknown handlers, dependencies on steps that do not exist, unknown YAML
   fields, and unworkable retry policies, reporting every problem at once.
2. **Application** — the state machine refuses illegal transitions, returning an
   error rather than panicking.
3. **Database** — CHECK constraints, unique constraints and foreign keys catch
   anything that got past the first two. A CHECK violation reaching the
   application is a bug, and `store.ErrCheckViolation` says so.

## Sensitive data and retention

ReLab stores **no personal data and no credentials**. The database connection
string is the only secret in the system; it is read from the environment, never
logged, and redacted out of driver error messages (`internal/store/redact.go`).

Handler outputs and artifacts are whatever a user's handlers put there. A
handler that returns a secret will have it stored in `tasks.output_ref` and in
the `TASK_SUCCEEDED` payload. `SECURITY.md` says so; ReLab cannot detect it.

**No retention policy ships in v1.** The journal grows without bound. A
deployment that runs ReLab continuously needs one; `DELETE FROM runs WHERE
completed_at < ...` cascades correctly.

## Encryption

At rest: whatever the PostgreSQL deployment provides. In transit: whatever the
DSN's `sslmode` specifies. ReLab adds neither, and does not pretend to.

## Migration strategy

Numbered `.sql` files, applied in ascending order, each in its own transaction,
under a session advisory lock so concurrent processes cannot race the same DDL.
Migrations are **never edited once released** — the checksum check enforces it —
and a new migration is added instead.

## Seed and test data

There is no seed data. Tests build what they need: `internal/testsupport`
creates a fresh database per test and migrates it, because the behaviour under
test is PostgreSQL's own (SKIP LOCKED races, advisory locks, constraint
violations) and a mock would only assert that the mock matches the test's
assumptions.
